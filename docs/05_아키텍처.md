# 05. Think Along 아키텍처

> Think Along의 제품 비전과 OpenClaw 벤치마크를 실제 구현 가능한 시스템 구조로 정의한다.

---

## 1. 아키텍처 목표

Think Along의 아키텍처는 하나의 목표를 중심으로 설계한다.

> **AI Provider가 변경되어도 사용자의 Session, Memory, Context, Decision, 작업 상태는 유지되어야 한다.**

GPT, Claude, Gemini 등은 Think Along의 핵심 시스템이 아니다.

이들은 Think Along이 필요에 따라 교체하여 사용하는 **Intelligence Engine**이다.

```text
                    USER
                      │
                      ▼
                THINK ALONG
                      │
        ┌─────────────┼─────────────┐
        │             │             │
      Session       Memory       Project
        │             │             │
        └─────────────┼─────────────┘
                      │
                      ▼
               Context Engine
                      │
                      ▼
                 AI Router
                      │
             ┌────────┼────────┐
             ▼        ▼        ▼
           OpenAI  Anthropic  Gemini
```

---

## 2. Architecture Principles

Think Along Core는 다음 원칙을 따른다.

### 2.1 Think Along Owns the Session

Provider가 Session을 소유하지 않는다.

잘못된 구조:

```text
OpenAI Session
      ↓
Claude Session
      ↓
Gemini Session
```

Think Along은 자체 Session ID를 가진다.

```text
ThinkAlong Session
      │
      ├── User
      ├── OpenAI
      ├── User
      ├── Anthropic
      ├── User
      └── Gemini
```

AI가 변경되어도 Session은 동일하다.

---

### 2.2 Think Along Owns the Memory

사용자의 장기 기억을 특정 AI Provider에 의존하지 않는다.

```text
                  Think Along Memory
                         │
              ┌──────────┼──────────┐
              ▼          ▼          ▼
            OpenAI    Anthropic   Gemini
```

Provider를 제거하거나 교체해도 Memory는 유지된다.

---

### 2.3 Context Is Provider Independent

각 AI의 API 형식은 다르지만 Think Along 내부에서는 하나의 표준 Context를 사용한다.

```text
                 ContextPack
                      │
          ┌───────────┼───────────┐
          ▼           ▼           ▼
     OpenAI Format Claude Format Gemini Format
```

Provider Adapter가 ContextPack을 각 Provider 형식으로 변환한다.

---

### 2.4 Providers Are Replaceable

새로운 AI를 추가할 때 Core Architecture를 수정해서는 안 된다.

```text
Think Along Core
       │
       ▼
Provider Interface
       │
 ┌─────┼─────┬─────┐
 ▼     ▼     ▼     ▼
GPT Claude Gemini Kimi
```

## 5. Unified Session

Session은 하나의 지속적인 대화 흐름을 나타낸다.

예:

```text
session_id
user_id
project_id
title
summary
status
created_at
updated_at
```

Message는 Session 아래에 저장한다.

```text
Message

id
session_id
role
content
provider
model
created_at
```

예:

```text
Session: S001

Message 1
USER
"Think Along을 설계하자."

Message 2
ASSISTANT
provider = openai

Message 3
USER
"Memory부터 보자."

Message 4
ASSISTANT
provider = anthropic
```

사용자 입장에서는 하나의 Conversation이다.

---

## 6. Project

Session보다 상위에 Project 개념을 둔다.

```text
Project

id
user_id
name
description
status
created_at
updated_at
```

관계:

```text
USER
 │
 ▼
PROJECT
 │
 ├── Session A
 ├── Session B
 ├── Session C
 │
 ├── Memory
 └── Decisions
```

하나의 프로젝트에 여러 Session이 존재할 수 있다.

이 구조가 필요한 이유는 Session이 종료되어도 Project Memory와 Decision은 유지되어야 하기 때문이다.

Memory 기본 구조:

```text

user_id
project_id
session_id

type
content

importance
status

created_at
updated_at
```

상세 구조는 `06_Memory.md`에서 정의한다.

## 8. Decision

Decision은 일반 Memory보다 강한 의미를 가진다.

```text
Decision

id
project_id

subject
value

status

superseded_by

created_at
updated_at
```

예:

```text
subject:
frontend

value:
Flutter

status:
SUPERSEDED
```

↓

```text
subject:
frontend

value:
React + TypeScript

status:
ACTIVE
```

Context Engine은 ACTIVE Decision을 우선한다.

## 9. Context Engine

Context Engine은 Think Along의 핵심 계층이다.

사용자의 메시지를 Provider에 그대로 전달하지 않는다.

```text
User Message
      │
      ▼
Context Engine
      │
      ├── User Memory
      ├── Project Memory
      ├── Active Decisions
      ├── Working Memory
      ├── Session Summary
      └── Recent Messages
      │
      ▼
ContextPack
```

ContextPack 예:

```typescript
interface ContextPack {
  system: SystemContext;

  userMemory: MemoryItem[];

  projectMemory: MemoryItem[];

  decisions: Decision[];

  workingMemory: MemoryItem[];

  sessionSummary?: string;

  recentMessages: Message[];

  currentMessage: Message;
}
```

Provider는 DB에서 직접 Memory를 읽지 않는다.

반드시 Context Engine을 통한다.

---

## 10. Context Engine의 역할

Context Engine은 크게 다섯 작업을 수행한다.

```text
Retrieve
   ↓
Rank
   ↓
Filter
   ↓
Compact
   ↓
Assemble
```

### Retrieve

현재 질문과 관련된 Memory를 가져온다.

### Rank

관련성과 중요도를 계산한다.

### Filter

불필요하거나 오래된 정보를 제거한다.

### Compact

Token Budget을 초과하면 Context를 압축한다.

### Assemble

최종 ContextPack을 생성한다.

상세 설계는 `07_Context_Engine.md`에서 정의한다.

---

## 11. AI Router

ContextPack 생성 후 Router가 실행된다.

```text
ContextPack
     │
     ▼
 AI Router
     │
     ▼
Primary Provider
```

Provider 실패 시:

```text
OpenAI
   │
   │ 429
   ▼
Router
   │
   ▼
Anthropic
```

중요한 점은 **ContextPack을 다시 만드는 것이 아니라 동일한 작업 Context를 다음 Provider에 전달한다는 것**이다.

## 12. Router MVP

```text
Gemini
```

초기 구현에서는 OpenAI + Anthropic 두 개만으로 시작할 수 있다.

```text

   ↕
Anthropic
```

상세 설계는 `08_AI_Router.md`에서 정의한다.

## 13. Provider Layer

Provider별 API 차이는 Adapter에서 처리한다.

공통 Interface:

```typescript
interface AIProvider {
  readonly id: string;

  chat(
    context: ContextPack,
    options?: ChatOptions
  ): AsyncIterable<AIChunk>;

  health(): Promise<ProviderHealth>;
}
```

구현:

```text
AIProvider

├── OpenAIProvider
├── AnthropicProvider
├── GeminiProvider
├── KimiProvider
└── LocalProvider
```

---

## 14. Provider Adapter 책임

Provider Adapter는 다음만 담당한다.

```text
ContextPack 변환

API 호출

Streaming 변환

Provider Error 변환

Usage 반환
```

Provider가 다음 작업을 해서는 안 된다.

```text
Memory 관리

Session 관리

Decision 관리

Context 검색

Routing 결정
```

이 영역은 Think Along Core의 책임이다.

## 15. Standard Error

Provider마다 오류 형식이 다르다.

이를 Router가 이해할 수 있는 공통 오류로 변환한다.

```typescript
type ProviderErrorCode =
  | "RATE_LIMIT"
  | "QUOTA_EXHAUSTED"
  | "TIMEOUT"
  | "AUTH_ERROR"
  | "PROVIDER_UNAVAILABLE"
  | "INVALID_REQUEST"
  | "UNKNOWN";
```

예:

```text
OpenAI 429

        ↓

OpenAIProvider

        ↓

RATE_LIMIT

        ↓

Router

        ↓

Anthropic
```

Router는 OpenAI API의 구체적인 오류 형식을 알 필요가 없다.

## 18. Response Streaming

사용자 경험을 위해 Streaming을 기본으로 한다.

```text
Provider

token
token
token
token

 ↓

Provider Adapter

 ↓

Standard AIChunk

 ↓

Client
```

예:

```typescript
interface AIChunk {
  type:
    | "text"
    | "usage"
    | "done"
    | "error";

  content?: string;
}
```

Provider별 Streaming API 차이는 Adapter에서 제거한다.

---

## 19. 실패 중 Streaming 문제

중요한 예외 상황이 있다.

AI가 답변을 절반 생성한 후 Provider가 실패할 수 있다.

```text
"Think Along의 Memory 구조는..."

                 X

              timeout
```

MVP에서는 무리하게 다른 AI가 문장 중간부터 이어 쓰게 하지 않는다.

안전한 방식:

```text
Partial Response
      │
      X
Provider Failure
      │
      ▼
Discard Incomplete Generation
      │
      ▼
Fallback Provider
      │
      ▼
Regenerate Response
```

사용자에게는 가능한 한 하나의 정상 Response만 남긴다.

향후 고도화 단계에서 partial continuation을 검토한다.

## 20. Memory Processing

AI 응답이 끝난 후 Memory 후보를 분석한다.

```text
Conversation Turn
       │
       ▼
Memory Candidate
       │
       ├── User Preference?
       ├── Project Fact?
       ├── Decision?
       └── Working State?
       │
       ▼
Memory Store
```

MVP 초기에는 모든 Turn마다 무거운 Memory AI 분석을 수행할 필요는 없다.

명시적인 결정과 중요 정보부터 저장한다.

## 23. Vector Database

MVP 초기부터 별도의 Vector Database 서버를 반드시 도입할 필요는 없다.

Memory 검색 규모가 작을 때는:

```text
PostgreSQL
+
pgvector
```

형태로 시작할 수 있다.

장점:

- Architecture 단순화
- 운영 비용 감소
- Memory + Vector 동시 관리
- Migration 용이

향후 데이터 규모가 커질 경우 별도 Vector Search 계층을 검토한다.

## 25. Modular Monolith

Think Along MVP는 **Modular Monolith**로 시작한다.

```text
Think Along Server

├── Session
├── Project
├── Memory
├── Decision
├── Context
├── Router
└── Providers
```

각 모듈의 책임은 분리하지만 하나의 애플리케이션으로 배포한다.

초기부터 다음처럼 Microservice로 나누지 않는다.

```text
Memory Service Server

Router Server

Context Server

Session Server
```
